# 插件性能优化

插件的启动和回调会与播放器共享进程。耗时工作可能拖慢界面或播放事件的处理，尤其是在播放器启动时自动启用多个插件的情况下。本文介绍如何减少插件对启动和运行流畅度的影响。

## 保持启动过程简短

`start()` 中应完成插件启用所必需的注册和轻量状态设置。播放器当前会在界面线程启动插件，因此同步读取大量文件、等待网络、扫描目录、解析大文件或执行复杂计算，都可能让界面暂时失去响应。插件构造函数、属性初始化和类的静态初始化也应避免执行这些工作。

按工作的性质安排线程：

- 文件读写、网络请求和其他阻塞操作使用后台 IO 线程，例如 Kotlin 协程的 `Dispatchers.IO` 或 Java 的 IO 线程池
- 大量解析、索引、排序和其他 CPU 密集计算使用后台计算线程，例如 `Dispatchers.Default` 或有界线程池
- 仅在需要访问界面或界面状态时，切换到对应 UI 框架要求的线程，并尽量只提交已准备好的结果

`start()` 不必等非必需的后台任务完成。可以先提供基本功能，再在结果就绪后更新状态。不要在启动或 UI 回调中使用 `join()`、`Future.get()`、`Thread.sleep()` 或 `runBlocking` 等方式等待后台任务，否则工作虽然在后台执行，界面线程仍会被阻塞。

::: warning 注册时机
快捷键需在 `start()` 线程内注册，Hook 注册也应遵守其启动生命周期和权限要求。不要把所有启动代码直接移动到后台线程。先在规定线程完成必要注册，再异步执行独立的耗时工作；具体约束见 [插件权限](permissions) 和 [直接 Hook API](hook)。
:::

## 管理后台任务的生命周期

为每次启用创建由插件持有的任务作用域或执行器，在 `stop()` 中取消任务、停止接收新工作并释放自己持有的资源。插件可以反复启停，不要重复使用已经取消的作用域或已经关闭的执行器，也不要让旧任务在下一次启用后覆盖新状态。

取消请求不一定能立即中断阻塞 IO 或第三方库调用。为网络操作设置超时，让长循环定期检查取消状态；交付结果前还应检查插件是否仍处于同一次启用以及结果是否仍然有效。检查与状态提交需要同步，避免停用和结果交付同时发生时出现竞态。不要在 `stop()` 中无限等待任务结束。

使用 Kotlin 协程时，不要把 `suspend` 当成自动切换后台线程：阻塞调用仍需放到适当的调度器。捕获异常时要继续传播 `CancellationException`，并处理后台任务的失败；Java 线程池需要处理任务失败、取消和中断，并在退出时关闭。

## 避免拖慢事件和 Hook 回调

回调的执行线程取决于具体接口，不要假定所有回调都在后台线程。普通方法 Hook 与目标方法在同一线程执行，UI Hook 的内容参与 Compose 界面组合，因此应保持轻量。播放位置等高频回调也不适合每次扫描文件、解析大型数据或发起网络请求。

- 提前准备可复用的结果，回调中只做必要的读取或状态更新
- 可以合并的频繁更新使用最新值、节流或批处理，避免排队积压；不要丢弃业务上必须逐条处理的事件
- 不要把只在当前同步调用期间有效的 Hook 参数保存或传给后台线程；需要异步处理时，只复制所需且允许保留的数据
- 需要同步返回结果的回调应在其契约允许的线程内完成，不能简单改为后台执行后立即返回。两个歌词加载回调已在 IO 线程运行，仍应控制超时和耗时

配置监听也不保证运行在 UI 线程。更新界面时切换到对应框架要求的线程，详见 [插件配置](configs)。Hook 的参数有效期、线程与注册方式见 [直接 Hook API](hook)。

## 测量与验证

在本地分别记录插件 `start()` 总耗时、耗时初始化步骤及高频回调耗时。Java 和 Kotlin 都可以用 `System.nanoTime()` 测量间隔；不要在高频回调中逐次输出大量日志，以免日志本身干扰结果。

在真实使用场景中验证播放器启动后是否能及时响应，并分别比较插件启用前后的表现。关注首次启动与再次启用的差异，也要检查网络慢、文件缺失、任务失败、启用后立即停用以及连续启停时的行为。后台任务应能正确取消或忽略过期结果，不应留下线程、监听器或重复注册。

宿主还可能在插件启动期间执行类加载和 Hook 安装等工作，尤其是首次使用相关能力时。插件自身的计时有助于定位问题，但单次启动日志不足以将全部等待时间归因于某个插件；必要时结合性能分析器和多次测量。
